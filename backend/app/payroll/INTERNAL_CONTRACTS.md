# Payroll internal contracts

This guide records cross-module helper contracts verified in the current backend source scan. These names are internal implementation contracts, not an external API. Production callers import the owner directly; tests keep their existing consumer-module monkeypatch seams. This guide and the owner module documentation add no aliases or facade.

## Cross-package internal contracts

| Owner | Supported helper | Consumers | Contract |
|---|---|---|---|
| `app.payroll.workflow_lock` | `acquire_branch_workflow_lock(company_id, branch_id, db)` | Payroll lifecycle/creation/finalization, Payroll Setup locks, Review decisions, eligibility/Workforce boundary operations, Driver-owned compensation writes | Takes PostgreSQL's transaction-level advisory lock keyed by `(company_id, branch_id)` on the caller's active connection transaction. It performs no authorization and does not begin, commit, or roll back the caller's transaction. |
| `app.payroll.guards` | `require_no_finalized_payroll(company_id, driver_id, footprint_from, footprint_to, mode, db)` | `compensation.schedules` approval/void; `payroll.driver_pay_rules` create/end/void | Read-only Driver-wide guard through `payroll.fn_DriverFinalizedPayrollTouched`: `Locked`/`Archived` periods with captured eligibility for any assignment of the Driver, in any Branch. Inclusive footprint, `None` unbounded, inverted footprint empty. `WorkDate` tests period overlap; `PeriodStart` tests the period start. Refuses with HTTP 422 / `DRIVER_COMPENSATION_IN_FINALIZED_PERIOD`. Owns no authorization, lock, commit, or caller ordering. |
| `app.payroll.guards` | `driver_payroll_period_branches(company_id, driver_id, from_date, db)` | `compensation.driver_context.lock_driver_compensation_write` | Lock-discovery twin of the finalized guard: both use `payroll.fn_DriverPayrollPeriodsForFootprint` over captured eligibility. Returns Branches of periods of any status overlapping `[from_date, infinity)` in `WorkDate` mode, a superset of `PeriodStart`. Writers lock the union of these Branches and live tenure Branches in ascending ID before row locks and the final authority/guard recheck; a timezone change must not exclude a captured historical period. |

## Payroll-package shared helpers

| Owner | Supported helpers | Verified consumers | Invariant to preserve |
|---|---|---|---|
| `app.payroll.eligibility` | `require_period_eligibility_snapshot`, `_is_snapshot_row_eligible_for_workdate`, `_assert_driver_eligible_for_workdate_via_snapshot`, `_assert_driver_eligible_for_period_via_snapshot`, `_create_period_driver_eligibility_rows`, `_regenerate_period_driver_eligibility_rows`, `append_driver_assignment_to_editable_periods`, `_driver_has_existing_daily_source_on_date`, `_lifecycle_eligible_assignment_ids` | Period creation/lifecycle, workforce writes, bonus, Day Grid, draft-line mutation, hub/off-driver/finalized-library reads, status sync; `test_cp2e_eligibility_snapshot.py` | Every operational period requires a tenant-scoped marker; missing marker fails closed with HTTP 409 and never falls back to a live roster. A valid empty snapshot is an intentional empty roster. Captured Branch-local eligible WorkDates are frozen; live assignment range and employment lifecycle may further restrict new input using the captured Branch zone. Existing-source rescue is exact-date only. `IncludedByExistingData` never grants new period-level Bonus authority. Draft-to-Open regeneration replaces provisional rows and freezes the snapshot. Workforce appends only the newly created DriverAssignment to editable marked periods; transfer cancel/reschedule may re-capture only the named assignment in overlapping Draft/Open/Returned periods under the boundary locks. |
| `app.payroll.day_entry_state` | `_validate_status_key`, `_upsert_entry_state`, `_enforce_status_key_limits` | Day Grid; canonical-entry and status-limit tests | Canonical entry-state writes preserve field ownership (`set_status`/`set_note`); a status-only or note-only write leaves the other field untouched. Usage-limit checks exclude overwritten batch slots and add the batch's new contributions separately. |
| `app.payroll.status_payment_sync` | `_sync_status_payment_for_entry_state`, `_refresh_status_payment_lines`, `_resolve_live_status_payment_lines` | Day Grid, period lifecycle, period calculation; canonical-entry and calculation snapshot tests | The persisted `STATUS_PAYMENT` draft line is a compatibility projection. Read-time calculation resolves live pay from canonical nonvoid entry states and effective Approved/Superseded rates, without writes; an entry state whose status has no rate column is omitted. Keep the shared arithmetic and sync/resolver distinction. |
| `app.payroll.bonus` | `_load_active_bonus_events` | Live Calculation packet and report-evidence capture; `report_read_model` LIVE path | Selects only Active canonical `PayrollBonusEvents` for the period and company on the caller's existing connection; retains the driver/employee and creator display joins, ordered `(driverassignmentid, payrollbonuseventid)` rows, and raw mapping objects. It opens no transaction and does not authorize or project the rows. |
| `app.payroll.period_calculation` | `_build_live_calculation_packet` | Period lifecycle, current hub, report read model; `test_cp5a_current_hub.py` patches the existing qualified builder seam | Builds the authoritative live packet and blockers without persistence. `_LiveCalculationPacket` is defined here and imported by `calculation_snapshot` for snapshot-writer typing; other packet dataclasses remain local. From DD3 the packet carries Company currency, official components (`payable-rounding-v1`) and Min/Max proration (`minmax-proration-v1`). Ordinary earnings are summed per DriverAssignment × PayDefinition × period, Status per DriverAssignment × status rate column × period, Bonus per DriverAssignment × period, and each rule adjustment separately; each component is rounded once with `round_payable` (`ROUND_HALF_EVEN`, stored currency digits). Line amounts retain internal precision; Driver totals sum official components without re-rounding. Min/Max uses the official ordinary + Status base, excludes Bonus, selects Driver-owned rules at period start and checks the home calendar, then prorates by frozen eligible scheduled days / scheduled days with D1 date ownership and Off reasons excluded. No day rows blocks Min/Max (`MINMAX_PERIOD_DAYS_MISSING`); zero scheduled days warns and skips rules, zero eligible days skips without warning. The packet retains raw/official values, rule/calendar context and versions for P4c; this does not enable immutable target evidence. `payroll/calculation/payable_rounding.py` is the only currency-rounding function. |
| `app.payroll.calculation_snapshot` | `_capture_calculation_snapshot` | Period lifecycle submit/resubmit | Freezes the calculation packet and the captured report evidence in the caller-owned transaction as one immutable snapshot (calculation contract `payroll-calculation-v2`): header with currency, both rule versions, period dates, frozen scheduled days and warnings; Driver totals with DriverAssignment/Driver/Employee/Branch identity; the official components (kind, target identity, pre-rounding and official amount); one Min/Max evaluation per Driver total with its rule and proration evidence; per-source lines (DraftLine, StatusEntryState, BonusEvent) with target rate provenance; and the used-rate evidence. It never recalculates, rounds or re-derives money, rejects blockers, and excludes generated IDs from the hash. Before returning it reads the snapshot back through `snapshot_verification.verify_snapshot`, so the hash recomputed from the persisted rows must equal the hash computed from the packet. System Min/Max lines of the packet are not persisted. The writer remains behind `TARGET_PAYROLL_EVIDENCE_NOT_READY`. |
| `app.payroll.snapshot_verification` | `load_snapshot_content`, `verify_snapshot`, `reconcile_snapshot_content` | Snapshot writer; approval, finalization and finalization preview | Rebuild the hashed content of one snapshot from its persisted rows alone, recompute the financial hash (`snapshot_hash.calculate_snapshot_hash`) and reconcile the evidence arithmetic. Fail closed with `SnapshotEvidenceError` (`UNSUPPORTED_CALCULATION_VERSION`, `SNAPSHOT_NOT_FOUND`, `SNAPSHOT_HASH_MISMATCH`, `SNAPSHOT_INTEGRITY_ERROR`, `UNSUPPORTED_PAYABLE_ROUNDING_VERSION`). Read-only; no live configuration is consulted. |
| `app.payroll.report_components` | `load_report_columns`, `load_financial_definition_columns`, `aggregate_definition_amounts`, `summarize_status_entries`, `report_error` | Live report and finalized-library report readers | Shared frozen-layout loading, derived-line aggregation, status grouping, and report error construction. In LIVE reports, `aggregate_definition_amounts` validates line/definition integrity; displayed definition money comes from the packet's official ORDINARY components, not the raw line sums. Frozen/finalized financial paths remain gated pending P4c. The readers retain their existing query and call order. |
| `app.payroll.finalized_context` | `FINALIZED_STATUSES`, `availability`, `finalized_error`, `get_finalized_period_context`, `resolve_originating_snapshot` | Finalized-library and finalized-audit readers | Performs finalized-period authorization/currency context and resolves exact FinalLines snapshot provenance. The singular approved-currency read remains distinct from the library page’s batched `_approved_currencies` query. |
| `app.payroll.finalized_audit` | `build_finalized_audit` | Finalized audit route | Preserves context/currency resolution before the evidence gate, then audit permission, provenance, availability, and audit evidence reads in their existing order. |

| `app.payroll.line_audit` | `_write_line_audit` | Bonus, Day Grid, draft-line mutation; batch-safety tests patch the existing `bonus` consumer binding | Keep audit writes in the caller's mutation transaction. |

The current scan also verifies local-only examples: `_CalculationPacketLine` and `_CalculationPacketDriverTotal` are defined and consumed inside `period_calculation.py`; `_LiveCalculationPacket` is defined there and imported by `calculation_snapshot` as the shared packet shape; `_snapshot_evidence` and `classify_final_line_component` are defined and consumed inside `finalized_library_read_model.py`. `_load_approved_snapshot_packet` is defined and consumed inside `finalization.py`. Test descriptions may name these helpers, but that alone does not make them cross-module production contracts. The shared contracts above do not remove lifecycle evidence gates or enable gated paths. This guide does not grant support status to other underscore-prefixed names.
