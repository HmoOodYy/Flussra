# Branch Timezone and Temporal Authority Contract

**Status:** Implemented cutover contract for migration `0086`; see the companion evidence report for baseline, schema, verification and remaining P4c gate. Amended 2026-10-18 for Durable Driver Stage 1 (permanent Driver, DriverAssignments and the Scheduled transfer lifecycle); the temporal rules themselves are unchanged.

**Scope:** Branch-local business dates, instant-based Driver assignments/transfers, and frozen payroll eligibility WorkDates.
**Supersession:** This document amends temporal assumptions in the People / Workforce / Access contract and its older master plan. It does not change payroll formulas, rate/setup effective DATEs, payroll period dates, termination/hire DATEs, WorkDate, event timestamps, or the Unified Plan's P4c evidence/finalization gate.

## Authority map

| Domain | Authority | Interpretation |
|---|---|---|
| Branch timezone | `core.Branches.TimeZoneId` | Required IANA/PostgreSQL regional identifier or UTC; exact identity is selected from `core.SupportedTimeZones`. No Company timezone/default exists. |
| Current business date | `core.fn_BranchToday(company, branch, instant)` | Tenant-scoped Branch lookup and canonical instant-to-date conversion. Missing Branch returns NULL; never falls back to Company or host/browser time. |
| Prospective Branch date | `core.fn_BusinessDate(time_zone_id, instant)` | Same SQL conversion before Branch persistence; invalid identifiers fail. Python helpers call SQL and do no timezone arithmetic. |
| Current Driver assignment | `core.fn_EffectiveDriverAssignment(company, driver, instant)` | Instant range `[EffectiveFromAt, EffectiveToAt)` of a permanent Driver's DriverAssignments determines the current home assignment; Employee-addressed callers map Employee to Driver first; SQL `NOW()` is the default transaction instant. |
| Payroll attribution | `BranchID + WorkDate` | A Driver assignment is eligible for that WorkDate when its instant range overlaps that Branch's entire local calendar day. Transfers do not create, split, prorate, or copy pay. Only explicit payroll inputs calculate compensation. |
| Frozen eligibility | `EligibleWorkDates DATE[]` and `BranchTimeZoneIdSnapshot` | Capture-time facts. Existing arrays and timezone snapshots never change when a Branch timezone changes. Current assignment bounds may still restrict new source inputs using the captured timezone's local-day boundary. |
| Payroll configuration | Setup/Version effective DATEs, rates, periods and planned dates | Company-owned chronology or explicit input dates; no inherent Company “today.” Contextual version reads may use a selected Branch's business date; without context `is_current` and reference date are NULL. |
| Employment and payroll inputs | HireDate, TerminationDate, WorkDate, period dates, rate/setup dates | Remain DATE values. No implicit timezone reinterpretation. |
| Audit and event history | `TIMESTAMPTZ` | Absolute event instants; browser timezone affects display only. JWT/host metadata instants remain valid. |

## Timezone registry and date conversion

Migration `0086` seeds `core.SupportedTimeZones` from PostgreSQL's installed `pg_timezone_names` catalog using the UTC/regional-prefix allowlist. The table is the DB-supported identity registry and FK authority for Branch zones and captured zones. PostgreSQL's timezone catalog and tzdata perform conversions; there is no Python `ZoneInfo`, static client list, runtime Company fallback, or TTL cache. Timezone conversion and local-day-to-instant boundary calculation stay in SQL; ordinary DATE chronology and ISO-date navigation remain pure DATE operations. A later tzdata refresh may add newly supported catalog identifiers with `INSERT ... ON CONFLICT DO NOTHING`; referenced identities are not deleted.

`core.fn_BusinessDate` is the only operational UTC-instant-to-business-date conversion. `core.fn_BranchToday` is tenant-scoped and never falls back. `core.fn_LocalDateBoundary` is the canonical local-midnight boundary resolver used by `core.fn_WorkDateRange`, including midnight folds; `core.fn_WorkDateRange` converts an inclusive DATE span to a half-open instant range by converting the next local calendar date before timezone conversion. The SQL boundary path handles 23/25-hour days, repeated midnight hours and skipped local dates without adding fixed UTC durations.

Branch timezone is editable and audited as normal Branch configuration. Updating it affects future/current clock evaluation but does not rewrite any DATE, event instant, frozen eligibility timezone, or frozen WorkDate array. No timezone history/effective-dating/default abstraction is introduced.

## Instant assignment and transfer

Driver assignment history is stored only as half-open instant ranges on `core.DriverAssignments`; each row is one continuous home-Branch tenure of a permanent Driver (`core.Drivers`). DATE-based Driver `EffectiveFrom`/`EffectiveTo`, DATE resolver overloads and DATE range functions are retired rather than retained as parallel authority. A transfer switches the source and destination assignments of the same Driver at one exact `EffectiveAt TIMESTAMPTZ`; immediate requests use database `NOW()` at completion, while an explicit future instant must still be future when the request is created and when it is scheduled. Source close and destination open use the identical instant, and no new Driver or driver number is created.

A future-dated transfer is `Scheduled`, not `Completed`. Completion materializes both windows at once (the source `EffectiveToAt` and the destination `EffectiveFromAt` both equal `EffectiveAt`, the destination remaining pending) and stores status `Scheduled`. The assignment windows are the single authority for currentness, so identity switches at `EffectiveAt` by time alone, exactly once, with no job. Request status is read through `core.fn_DriverTransferStatus(status, effective_at, at)`, which reports a stored `Scheduled` request as `Completed` once `EffectiveAt <= at`; its completed instant is `EffectiveAt`. Until `EffectiveAt` the transfer may be cancelled (the never-effective destination assignment is deleted and the source reopened) or rescheduled (both boundaries move and the destination assignment keeps its identity); neither is possible afterwards or once the Employee is terminated. Both are refused when payroll facts or non-editable periods would be affected, as described under Frozen eligibility and lifecycle.

Decision instant: every future/past decision of a transfer operation (complete, cancel, reschedule, termination) uses one `clock_timestamp()` read after all locks are held, never the transaction-start `NOW()`; the immediate boundary is that instant. `trg_DriverAssignments_HistoryImmutable` tests started/ended/future against `clock_timestamp()` too, so the database is at least as strict as the application. The only bound left on `NOW()` is that an open assignment is not closed before the transaction start. Display and read paths keep the `NOW()` default.

Current Driver identity, Employee Branch projection, administrative current-linked Driver views and Driver Self authorization resolve against the same instant resolver. Historical payroll eligibility is WorkDate-based and must not cast an instant to a DATE. Termination remains an explicit DATE and caps each DriverAssignment in its own Branch at `core.fn_LocalDateBoundary(assignment_branch_zone, TerminationDate + 1)`, including a skipped local date, and records `EndReason = 'Terminated'`. Empty future assignments may be retained only as empty Terminated assignments; they grant no new payroll-source or Bonus authority. A `Scheduled` transfer whose `EffectiveAt` is at or after the source Branch's termination cutoff is disposed of: the request is `Cancelled` with no destination, the destination assignment is deleted and the source ends at its cutoff as `Terminated`; one whose `EffectiveAt` is before the cutoff stays and is effectively `Completed` at `EffectiveAt` (and can no longer be cancelled or rescheduled).

Branch settings people counts use the same instant projection policy in a read-only query. They count each Employee under the current Driver Branch when one resolves, otherwise retain the stored Branch for non-Driver employees or the latest ended nonempty Driver Branch for a terminated Employee. Reading metrics does not synchronize or lock Employee rows.

An assignment may cover both source and destination Branch local days around a midday transfer. That permits explicit WorkDate/source entries in both Branches where the instant ranges overlap each local day; the transfer itself never generates financial rows. Half-open bounds mean an assignment ending exactly at the next local day's start does not cover that next day.

## Frozen eligibility and lifecycle

Every valid PayrollPeriod has its tenant-scoped eligibility marker. A missing marker is structurally invalid and fails closed; reads never rebuild or fall back to a live roster. Capture materializes the period's calendar DATEs using SQL integer offsets and stores exactly those WorkDates whose Branch-local day intersects the Driver assignment, subject to employment DATE gates. Frozen rows and arrays are immutable after capture, including when a Branch timezone changes. The existing Draft-to-Open promotion intentionally regenerates provisional roster rows and freezes the resulting capture. `IncludedByExistingData` remains an exact-date rescue classification and does not authorize new period Bonus entries.

An explicit Workforce assignment creation or transfer completion may append only the new destination/assignment roster row to source-editable periods (`Draft`, `Open`, `Returned`) that already have a marker. Capture reuses the canonical snapshot SQL with an only-Driver filter; existing rows and frozen date arrays are untouched. Review states stay immutable. Lock order is Branch workflow advisory lock followed by PayrollPeriod row locks in ascending ID; the helper takes neither Employee nor currency/compensation locks.

Cancelling or rescheduling a `Scheduled` transfer is the one narrow exception, alongside the append rule, that may re-capture an existing roster row. It applies only to the named assignment (the reopened source on cancel; the source and the destination on reschedule), reuses the same canonical snapshot SQL with an only-assignment filter, and works only inside source-editable periods (`Draft`, `Open`, `Returned`) of that assignment's Branch that overlap the affected interval. A period in review, approved, locked or archived state that overlaps the affected interval, or any payroll fact of an assignment on WorkDates its changed window no longer covers, makes the operation refuse with a conflict. A `Cancelled` period is reachable only from `Draft` or `Open`, so it never carries submissions or evidence: it neither blocks nor is re-captured, and the roster rows of a never-effective destination in it are deleted with the editable ones. Nothing in a non-editable period is rewritten, and rows of other assignments and the frozen arrays of unaffected rows stay untouched. Every coverage-shrinking operation (transfer completion, cancel, reschedule, termination) locks the PayrollPeriod rows overlapping what it removes or moves before it changes a window (completion and termination take the locks without any state-based refusal); source writers take the period row lock first and re-check eligibility under it, which makes either order safe. These operations lock the Employee, the transfer request, that Driver's assignments in ascending ID, the Branch workflow advisory locks in ascending BranchID, and then PayrollPeriod rows in ascending ID.

Boundary changes (transfer completion, cancel, reschedule, termination) use the frozen authority, not the Branch's current zone alone. Period discovery (which PayrollPeriod rows to lock, state-check and re-capture) treats a period as overlapping a window when its WorkDate range overlaps it under any governing zone: each distinct `BranchTimeZoneIdSnapshot` of the period's eligibility rows, plus the Branch's current zone (future appends and captures use it). Coverage verification judges every daily fact and Active Bonus with the zone captured on the assignment's row of that period (the current zone only when the period has no row for it), through one shared window-versus-day predicate that lifecycle eligibility also applies. Re-capture keeps the replaced row's captured zone and recomputes its dates under it; only brand-new rows use the current zone.

New payroll source checks intersect the live assignment instant range with the frozen Branch timezone's WorkDate range, in addition to existing employment/hire/termination/status rules. Captured timezone/date authority is immutable even if Branch timezone is edited later. A new Bonus requires at least one captured WorkDate that still overlaps the live nonempty assignment. Existing exact-date saved-source rescue remains unchanged.

## Clean cutover and evidence gate

Migration `0086` refuses before DDL when any Driver profile, DriverTransferRequest, or PayrollPeriod exists (`BRANCH_TIMEZONE_REBUILD_REQUIRED`). The old DATE history cannot be truthfully translated into instants and old frozen payroll evidence cannot be rewritten. Rebuild the preproduction database or explicitly correct invalid legacy Branch timezone configuration before retrying; the migration does not invent transfer times or default to UTC. Branches without Driver history and Employees without profiles may remain. The Durable Driver Stage 1 migration follows the same clean-cutover pattern.

This refoundation did not complete P4c. Target payroll submit, resubmit, finalization, finalization preview and immutable evidence stayed blocked under the `TARGET_PAYROLL_EVIDENCE_NOT_READY` gate until P4c delivered immutable calculation evidence (migration `0089`) and removed that gate.
